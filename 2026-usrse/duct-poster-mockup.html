The agent drives, you read the summary

The agent writes a reproducer and runs it under duct, numbering each step in the tag:

$ duct -p logs/1_ -m "1: reproduce user's bug"                      ./repro.sh
$ duct -p logs/2_ -m "2: simplified reproducer to test hypothesis"  ./repro.sh
$ duct -p logs/3_ -m "3: verify fix"                                ./repro.sh

The agent reports “fixed”. You do not take its word:

What is con-duct?

con-duct is a lightweight command-line wrapper that records what a command printed and the resources it used, for any command, with no code changes. Its companion commands let people and agents find those records later, query them, and plot them.

Capture now, ask questions later

Wrap it: duct <cmd> instead of <cmd>. The command runs unchanged, its output still reaches your terminal (like tee), and it leaves four files.

$ duct my-fancy-command-or-script
→
your terminal, as before
stdoutstderrinfo.jsonusage.jsonl
  • stdout, stderr: everything the command printed, in full.
  • info.json: run metadata and summary, e.g. command, exit code, wall time, peak memory and CPU.
  • usage.jsonl: resource use over time, one line per report: memory and CPU for each process in the tree, and their totals.

Resource usage is recorded too. duct samples the whole process tree every second and writes a report every minute: peak and average memory and CPU, per process and in total.

Record everything, read it later if helpful. Humans and agents now run commands side by side. Without a record, the terminal output is either bloating an agent's context window or gone past the scrollback.

Search and retrieve duct records

Every record is a small JSON file. con-duct ls reads them all and answers questions across runs, machines, and months, for you or for an agent.

Which jobs failed, and how long did they burn first?

$ con-duct ls -e "exit_code != 0" \
    -F command exit_code wall_clock_time

Structured output for scripts and agents:

$ con-duct ls -f json logs/ | jq …
  • Filter with any Python expression over the 40+ fields (-e); pick columns (-F); sort by any field (--sort-by).
  • Output as a table, JSON, or YAML (-f).
  • No database: point it at directories, or let it find records by your output prefix.

Adopted inside tools

Tools wrap their own runs so users get records without asking.

  • BABS github.com/PennLINC/babs
    Wraps every BIDS App job on SLURM and copies the record next to each subject's results. Why: per-subject peak memory and wall time to size the next batch; the app's stdout and stderr, with its warnings and other internals, for inspecting any job later.
  • ReproNim/containers github.com/ReproNim/containers
    REPRONIM_USE_DUCT=1 wraps each Singularity container run, e.g. under datalad containers-run. Why: a resource record for every containerized app run, saved with its results.
  • ReproStim github.com/ReproNim/reprostim
    The video-capture app wraps each ffmpeg recording (on in the default config); the record sits next to the video. Why: resource use for long, unattended capture sessions.

Limitations

  • Output is written to disk: do not wrap commands that print secrets.
  • Programs that check isatty() take their non-interactive path (README has workarounds).
  • Sub-second commands leave four files and no samples. POSIX only; ps numbers are approximate; cgroup measurement in progress (con/duct#438).
  • A process that lives a few ms is invisible to a 1 s sampler, duct's own ps included: the overhead panel's time -v total is nearly twice what duct saw of itself.
  • Resource peaks paid off on SLURM; for agentic work the value has been the logs and con-duct ls. Wrap the runs you cannot afford to repeat.
