The agent drives, you read the summary

The agent writes a reproducer and runs it under duct, numbering each step in the tag:

$ duct --f-t 0 -p logs/1_ -m "1: reproduce user's bug"  ./repro.sh
$ duct --f-t 0 -p logs/2_ -m "2: test hypothesis"       ./repro.sh
$ duct --f-t 0 -p logs/3_ -m "3: verify fix"            ./repro.sh

The agent reports “fixed”. You do not take its word:

What is con-duct?

con-duct is a lightweight, open-source (MIT) command-line wrapper that records what a command printed and the resources it used, for any command, with no code changes. Wrap a command with duct <cmd>, short for con-duct run <cmd>; companion commands such as con-duct ls and con-duct plot let people and agents find those records later, query them, and plot them.

Later, you or your agent ask:

con-duct ls -e "exit_code != 0"
Why did it fail?

How much did it need?

just the lines that matter, so the agent's context stays small
memory and CPU over time, for any run
Nothing is re-run: the answers were recorded the first time.

Adopted inside tools

Tools wrap their own runs so users get records without asking.

  • BABS github.com/PennLINC/babs
    Wraps every BIDS App job on SLURM and copies the record next to each subject's results. Why: per-subject peak memory and wall time to size the next batch; the app's stdout and stderr, with its warnings and other internals, for inspecting any job later.
  • ReproNim/containers github.com/ReproNim/containers
    REPRONIM_USE_DUCT=1 wraps each Singularity container run, e.g. under datalad containers-run. Why: a resource record for every containerized app run, saved with its results.
  • ReproStim github.com/ReproNim/reprostim
    The video-capture app wraps each ffmpeg recording (on in the default config); the record sits next to the video. Why: resource use for long, unattended capture sessions.

Overhead

About 2–3 % of one core and 37 MB of memory, watching 1 to 256 processes.

Measured by running duct under duct on a laptop (i7-1280P): N idle processes, 5 min each, 1 s sampling. The table is duct's python process (± is the ps rounding bound); the whole run, its own ps calls included, was 3.3 % of one core. The rise past 16 processes is consistent with a slow increase, not a measured slope.

Limitations

  • Linux and macOS only.
  • On macOS, ps cannot filter by session, so each sample scans every process on the machine: more overhead than on Linux.
  • Output is written to disk; for commands that print secrets, skip it with -c none.
  • Programs that check isatty() take their non-interactive path (README has workarounds).
  • CPU statistics come from ps, whose %CPU is averaged over each process's lifetime rather than its current use; con-duct plot --cpu ps-cpu-timepoint estimates current use from consecutive samples.
